Базовая модель `Qwen/Qwen3-0.6B`, revision `c1899de289a04d12100db370d81485cdf75e47ca`. Фактическое число базовых параметров: **596,049,920**. LoRA: 10,092,544 обучаемых параметров. Диапазон менторов 500 млн–1,5 млрд соблюдён; это размер всей модели, не только адаптера.

Обучение: 3334 fit-звонка, 3635 окон, 5,060,943 токенов на эпоху. Dev: 592 звонка; пересечение аккаунтов — 0. Запрошено эпох: 2, выбранная эпоха: 2. Выбор checkpoint: response token loss on first 96 internal dev calls; no external val selection. Выбор дат на полном dev: `date_ranker`.

Модель генерирует компактный JSON фактов с источниками. Даты, спаны, ID объектов и цепочки состояний восстанавливаются общим постпроцессором. Длинные звонки разбиваются на окна с перекрытием; метки и будущие звонки на вход не передаются. Потери считаются только по ответу.

Для фрагментов до пяти реплик при пустом ответе Qwen включается консервативный резерв правил для явно названного тарифа из каталога и подтверждённого выезда. Это не дополнительная нейросеть; применение отмечено в generation_diagnostics.short_rule_fallback и в демо. Общая обработка коротких фрагментов остаётся ограничением.

Исправлены некорректные обучающие имена/типы объектов: 616. Скрытые ID аккаунтов не используются как генерируемые имена.

## Ресурсы

Сравнение задержки систем на одинаковых 24 dev-звонках, CUDA, batch=1:

| Система | Звонки | Среднее, мс | p95, мс | Пик RSS процесса, МБ | Пик CUDA, МБ |
|---|---:|---:|---:|---:|---:|
| Qwen3-0.6B | 24 | 6562.3 | 8975.1 | 2014.7 | 2473.9 |
| Прежний гибрид ~94M | 24 | 179.9 | 506.5 | 2436.0 | 718.9 |

Одинаковые первые 24 звонка внутреннего dev, 6 CPU threads. В cuda_batch4 время/звонок — доля времени пакета, а не задержка онлайн-запроса. Остальные режимы — batch=1. Время включает генерацию и обработку дат; загрузка весов и файловый ввод-вывод исключены. Первый запрос включён. Пик RSS процесса измерен средствами ОС и включает загрузку модели; отдельные замеры RSS после звонков также сохранены в JSON.

Питание от сети и состояние GPU записаны в hardware_start/hardware_end ресурсных JSON. Во время предварительной проверки ноутбук работал от батареи с ограничением GPU около 30 Вт; этот участок не используется для контрольного сравнения скорости.

INT8 — поканальная динамическая квантизация, экспериментальный режим. На одном dev-примере первого checkpoint поканальный вариант восстановил JSON после ошибки обычного INT8, но содержание оставалось хуже FP32. Протокол: `reports/qwen_int8_preflight.json`. Рабочие варианты — CUDA BF16 и CPU FP32; результаты INT8 не переносятся на них.

Ошибки генерации по режимам на этих 24 звонках: `{"cuda": {"invalid_json_windows": 0, "invalid_rows": 0, "truncated_windows": 0}, "cuda_batch4": {"invalid_json_windows": 0, "invalid_rows": 0, "truncated_windows": 0}, "cpu": {"invalid_json_windows": 0, "invalid_rows": 0, "truncated_windows": 0}, "int8": {"invalid_json_windows": 16, "invalid_rows": 1, "truncated_windows": 8}}`.

## Границы выводов

- Прежний гибрид обучен на полном выданном train; Qwen — только на fit, поскольку dev оставлен для независимого выбора. Сравнение отражает готовые системы, не изолированный эффект архитектуры.
- Даты без точного дня сохраняются отдельно в `temporal_evidence` API; конкурсная метрика требует точечных дат.
- Некорректный JSON не превращается в придуманные факты; такие окна учитываются в диагностике.
- Размер, скорость и качество не взаимозаменяемы: соответствие диапазону параметров само по себе не доказывает превосходство.
- Замеров LLM-учителя нет. Снижение затрат в 5/10 раз не подтверждено.

Воспроизведение: `docs/QWEN.md`. Базовые веса скачиваются отдельно с проверкой revision и SHA-256; LoRA-адаптер, метаданные и скрипты сохранены в проекте.
