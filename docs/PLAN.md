## Отправная точка

Первый CPU-прототип нужен для проверки всей цепочки: train -> веса -> независимый
инференс -> JSONL -> официальный оценщик -> анализ ошибок. Он не заменяет итоговую
нейросетевую модель и пока не доказывает выполнение всех критериев хакатона.

Архитектура: символьный TF-IDF (3–5 символов, 100 тыс. признаков), пять линейных
классификаторов реплик, поиск похожих обучающих примеров для нормализации значений,
сопоставление объектов со словарём из train, правила относительных дат и временных
интервалов. Контекст содержит текущую и соседние реплики, роль говорящего.
Источник факта всегда указывает на реальную входную реплику; span пока равен всей
реплике и не является точным выделением аргумента.

## Следующие эксперименты

1. Обсудить с организаторами отсутствие `catalog.json`, расхождение опубликованных
   и пересчитанных метрик, цитаты вне реплики и тип объектов `other` в эталоне.
   Ошибки цитат могут быть следствием ASR-преобразования после разметки; автоматически
   объявлять такие факты неверными нельзя.
2. Проверить span-разметку до обучения энкодера: сначала выровнять чистые цитаты
   с шумной репликой, сохранять уверенность, спорные примеры выделить отдельно.
3. Обучить небольшой предобученный русскоязычный/многоязычный энкодер с головами
   attribute / polarity / source / object / value. Выбирать конкретные веса после
   проверки лицензии и фактического потребления памяти. На этой машине RTX 3060
   Laptop 6 ГБ; полноразмерный teacher здесь не планируется.
4. Добавить извлечение открытых значений вместо выбора только среди фраз из train:
   в val много новых формулировок. Отдельно улучшить договорённости с подтверждением,
   отказы, тарифные переходы, несколько объектов и межзвонковую память.
5. Даты: извлекать выражения и связь с конкретным событием; разрешать календарные
   неоднозначности отдельно от уверенности в факте. Не восстанавливать отсутствующие
   в тексте старые даты запоминанием обучающих значений.
6. Сравнить минимум три настоящих режима ресурсов: разные длины контекста,
   квантование/размеры энкодера или отключение retrieval. Текущие три порога дают
   только кривую precision/recall с разным количеством кандидатов, не заменяют
   полноценную кривую разных архитектур.
7. Провести абляции: без контекста / без нормализации / без дат; стресс-тест с
   дополнительными искажениями ASR. Это локальный стресс-тест, не скрытый тест жюри.
8. Повторить CPU- и GPU-замеры по одной методике, проверить Docker, подготовить
   презентацию и демонстрацию. Финальные качество и экономию заявлять только после
   этих измерений. Без замеров учителя нельзя честно заявить ускорение в 5–10 раз.

## Как трактовать официальный оценщик

`data/raw/case_metrics.py` скопирован без изменений.

- В `match_facts` имя объекта разбивается на символы через `" ".join(name)`,
  после токенизации сравнивается первый символ. Условие `or not osim` также допускает
  пары с нулевой похожестью. Это ограничение метрики, не механизм нашего извлечения.
- `state_accuracy` выбирает последний факт по атрибуту среди всех объектов звонка,
  а не по идентификатору отдельного объекта. При нескольких объектах возможны
  некорректные совпадения/штрафы.
- `temporal_recall` делится только на количество сопоставленных фактов, а не на
  все эталонные факты с датами. Поэтому её нужно читать вместе с fact_recall.
- `grounding_span` проверяет любое пересечение интервалов. Полная реплика часто
  получает высокий балл, хотя точный аргумент ещё не выделен.

Дополнительные диагностические показатели в `scripts/evaluate.py` не меняют
официальный результат. Вопросы по методике нужно адресовать организаторам;
самостоятельно исправлять их оценщик для основного сравнения нельзя.
