# Проверка дат через API после выбора модели

Начальный результат сохранён в `reports/date_pointer_api_check_initial.json`:
не прошли окно выезда и старое ожидание точных дат цепочки статусов.

В старом шумном примере дата 4 апреля не названа как начало текущего статуса.
Упоминание субботы относится к подтверждению по SMS. Требовать эту дату для
перехода состояния было ошибкой тестового эталона. Для проверки точных границ
добавлен отдельный разговор, где прямо сказано «принята 31 марта» и «с 4 апреля
в работе». Исходный шумный разговор также проверяется: неозвученное начало
другого состояния должно отображаться как неизвестное.

Если в одной реплике перечислено несколько состояний, дата, выбранная для
первого, больше не считается доказательством начала остальных. Конкурсные
точечные прогнозы при этом сохраняются; интерфейс явно отмечает неопределённость
в `temporal_evidence`. Это не превращает ошибочную точечную дату в правильную
и не повышает официальную метрику само по себе.

Для выезда восстановление окна использует уже выбранную моделью ссылку на
предложение оператора и принятие предложения клиентом. При повторном подтверждении
оператором сохраняется названное «до 18:00». Отказ и новое конфликтующее окно
блокируют перенос. Проверяются реальная цитата, совпадение начала, порядок
реплик и небольшой контекст подтверждения; другие звонки не используются.
Источник окончания помечается как `confirmed_offer_window`.

Исправление сделано после фиксации checkpoint и режима дат. Повторного обучения
и подбора модели по val не было. `scripts/replay_date_refinement.py` сверяет
сохранённые ответы: на 592 dev и 383 val не изменён ни один объект конкурсного
факта, обновлены только вспомогательные сведения о неопределённости. То же
проверено для ASR-контроля и трёх наборов замеров ресурсов. Официальные метрики
и веса оставлены без изменений. Аудит содержит SHA-256 фактов и время работы
добавленного CPU-обработчика.

Замеры ресурсов выполнены перед этой небольшой правкой постпроцессора;
добавленные накладные расходы измерены отдельно в
`reports/date_pointer_api_refinement_audit.json`. Новый inference автоматически
применяет обработчик; replay нужен для старых сохранённых ответов.

```powershell
.venv/Scripts/python.exe scripts/replay_date_refinement.py
.venv/Scripts/python.exe scripts/check_qwen_api.py --url http://127.0.0.1:8001 --output reports/date_pointer_api_check.json --expected-adapter artifacts/qwen_dates --extended
```

Итог: семь HTTP-сценариев, 11 проверок. Подробные ответы и состояние модели —
в `reports/date_pointer_api_check.json`. Успех этих сценариев не означает
прохождения порогов качества на всём val.
